# macOS port decisions

## D1: UIKit module packaging (Task 1 spike, 2026-10-13)
Result: module named UIKit works, provided the framework product is also named UIKit (PRODUCT_NAME: UIKit, PRODUCT_MODULE_NAME: UIKit). No fallback needed.
Evidence: with PRODUCT_NAME: ConduitUIKitCompat the build failed with
`ProbeApp.swift:2:8: error: Unable to resolve module dependency: 'UIKit'`
(Swift locates a framework module by framework directory name, UIKit.framework, not by module name). After setting PRODUCT_NAME: UIKit: `** BUILD SUCCEEDED **`; Debug products contain UIKit.framework; the app launched (pgrep -x Conduit returned a pid).

## D2: AVAudioSession shadowing (Task 1 spike, 2026-10-13)
Result: same-named class in app target shadows AVFAudio
Evidence: probe declared `final class AVAudioSession` in the app module alongside `import AVFAudio`; no ambiguity error, `** BUILD SUCCEEDED **`.

## D3: SwiftUI-only upstream files and the UIKit module (Task 6, 2026-10-13)
Result: ConduitMac builds with `OTHER_SWIFT_FLAGS = -Xfrontend -import-module -Xfrontend UIKit`, so the shim module is visible in every file. Upstream view files that `import SwiftUI` only (iOS SwiftUI re-exports UIKit) then resolve UIImage, UIPasteboard, UIKeyboardType, UIUserInterfaceIdiom and the rest without an upstream `import UIKit` line.
Evidence: before the flag, errors such as `cannot find type 'UIImage' in scope` in BotEditorSheet.swift, ProfilePickerSheet.swift, ChatSupportSheets.swift, SidebarLayout.swift; after: gone, no upstream edit.
Two side effects, both handled in project.yml:
- The SDK has a cross-import overlay for AppIntents + a module named UIKit (`_AppIntents_UIKit`). macOS has none, so every file importing AppIntents failed with `no such module '_AppIntents_UIKit'`. Fix: an empty framework target `AppIntentsUIKitOverlay` (PRODUCT_NAME `_AppIntents_UIKit`), sources in ConduitMac/Compat/Overlay.
- Explicit module builds cannot see the SDK cross-import overlays (`no such module '_AppIntents_AppKit'`), so `SWIFT_ENABLE_EXPLICIT_MODULES: NO` on ConduitMac. Removing it reproduces the error.

## D4: iOS-only SwiftUI API (Task 6, 2026-10-13)
Result: same-named declarations in the app module shadow the SDK's macOS-unavailable ones, including types (`NavigationBarItem`), static members (`ToolbarItemPlacement.topBarLeading`) and View methods (`navigationBarTitleDisplayMode`, `fullScreenCover`). No call-site edits were needed. File: ConduitMac/Compat/App/SwiftUIiOSModifiers.swift.
Mappings: topBarLeading -> .navigation, topBarTrailing -> .primaryAction, `.navigationBar` -> no-op (see below), fullScreenCover -> sheet, textInputAutocapitalization and keyboardType -> no-ops.
Correction (titlebar fix): `navigationBar` was first mapped to `.windowToolbar`, so upstream's `.toolbar(.hidden, for: .navigationBar)` (7 sites) and `.toolbarBackground(.hidden, for: .navigationBar)` (9 sites) hid the window toolbar and title bar, traffic lights included, once the persistent sidebar (SidebarView.swift:161) was in the main window. Mac windows have no iOS nav bar and the chrome must stay, so `.navigationBar` now lives on `MacNavigationBarPlacement`, with app-target `toolbar(_:for:)` and `toolbarBackground(_:for:)` overloads that return `self`. Guard: ConduitMacTests/WindowChromeTests.

## D5: Hover accessibility layer (2026-10-13)
What it does: `HoverAccessibilityEngine` (ConduitMac/Accessibility) installs one app-wide local event monitor. SwiftUI builds a window's accessibility tree only while an assistive client is attached, so the engine reads the element under the pointer through that tree and shows a tooltip from its label, a pointing-hand cursor over controls, and an optional highlight.
Undocumented selector: AppKit's enhanced-UI flag, `accessibilityEnhancedUserInterfaceAttribute` / `accessibilitySetEnhancedUserInterfaceAttribute:`, called with `perform` (no KVC; KVC raises `NSUnknownKeyException` on `SwiftUI.AppKitApplication`). Only `AccessibilityTreeBoost` names them.
Scoped and owned: the flag is turned on only while the pointer is moving over the key window of the active app, and off after 2 s idle, on click or key, and on deactivation. The engine tracks ownership and never clears a flag it did not set. It never clears the flag while `NSWorkspace.isVoiceOverEnabled` is true; it gives up ownership instead.
Kill switch: `defaults write com.meswan.hermes.mac conduit.mac.hoverTooltipsDisabled -bool YES` (read at launch; the engine is not installed).
Risks: undocumented API that Apple can change or remove; verified only on macOS 27. If the selectors stop answering, the engine logs a warning and tooltips degrade silently. While the flag is on AppKit may slow window animations.

## D6: Mac split layout (2026-10-13)
Result: on Mac the persistent-sidebar branch of `RootView.sidebarLayoutContent` is a `NavigationSplitView` (`MacSplitLayout`, ConduitMac/App/MacSidebarState.swift) instead of the fixed-width HStack. The sidebar column is user-resizable via `.navigationSplitViewColumnWidth(min: 260, ideal: 340, max: 390)`. Column visibility is bound to `@AppStorage("conduit.mac.sidebarVisible")` (default true; `.all` vs `.detailOnly`). Toggle Sidebar (Cmd-Ctrl-S) flips that key. `conduit.ipadPersistentSidebar` stays registered true by `MacDefaults` so the persistent path is always taken; it no longer has a Mac toggle.
Detail routing: the sidebar always shows `SessionList()` (SidebarView gate). The existing tab picker writes `conduit.sidebarTab`; `MacDetailRouter` maps it through `SidebarTab.migrated(rawValue:)` to chat, `BotRosterView`, `CronList` or `KanbanView` in the detail column. Opening a session (`AppState.activeSessionId` becomes non-nil) or a group-chat room (`activeRoomSurface`) sets the tab back to Sessions.
Fix round 1: chat stays mounted under the other panes (ZStack, opacity 0, no hit testing, hidden from accessibility) so draft, scroll and backfill survive tab switches. Tapping in the session list returns to Sessions, since re-selecting the active session fires no `onChange`. Programmatic opens (Cmd-N, deep links, Kanban card) also return to chat (R33). The detail column has a 430 pt minimum width. Mac `sidebarPresentation` is always `.persistent`.
Cron search: `CronList.searchable` crashes when mounted beside the sessions `.searchable` (two window search toolbar items). Mac uses an inline TextField (SidebarView gate, ledger). Hosting CronList in a separate NSHostingView/NSHostingController with `sceneBridgingOptions = []`, or in a NavigationStack, did NOT avoid the crash. Launch note: a restored session (`activeSessionId` changes) returns the tab to Sessions, so a persisted Bots/Cron/Kanban tab does not survive a relaunch once the session restores.
Fix round 2 (route-aware chat): the hidden chat must not leak chrome into the window. Mechanism: `MacChatRoute` (ConduitMac/App/MacChatRoute.swift) maps the `conduit.sidebarTab` key to "chat is the shown pane". Upstream chat code reads that key (`MainView.chatPaneActive`, `GroupChatView`, the Mac composer twin) and, while another pane is shown, drops the chat toolbar items (title pill, Refresh, connection status; the sidebar's `.searchable` "Search sessions" field is owned by the always-visible sidebar and stays), sets the window title to the pane name, pauses the chat backdrop (`drifts: false`) and refuses/resigns composer first responder. Routing back to chat on session open no longer uses a whole-list tap gesture: `AppState.requestOpenSession` posts `.macSessionOpenRequested` (re-opening the active session changes no state), and the router returns to Sessions on it. Column metrics live in `MacSidebarState`: sidebar 260/340/390 and detail min 430 fit the 820 window minimum (guarded by MacChatRouteTests); the sidebar max dropped from 480 for that reason. Pane headers: `MacPaneHeader` and `MacSearchPill` (ConduitMac/Views/MacPaneChrome.swift) give Bots and Cron Kanban's title and search treatment.
Fix round 2a: focus a hidden chat held is restored on return (ComposerTextView `resignForRoute` / `restoreFocusIfHeld`; skipped when a sheet is attached or another text input is first responder). `openBotChat` posts the same session-open signal. RootView's chat chrome is `#if os(macOS)` gated so the iOS path is the original code (toolbar items moved verbatim into `chatToolbarContent`).

Pane title (2026-10-14): Bots, Cron and Kanban showed the pane name twice, as the window toolbar title and again as the pane's own header (which carries the board subtitle and the actions). The headers stay. On macOS 26 and later the toolbar no longer displays the title: `RootView`'s always-mounted chat `NavigationStack` applies `macHidingToolbarTitle`, which is `toolbar(removing: .title)` while a pane other than chat is the route (SwiftUI turns it into `NSWindow.titleVisibility = .hidden`). The window keeps its title string, the pane name, for the Window menu, Mission Control and accessibility, and the chat route is unchanged (title empty and visible, no toolbar item added or removed). The same modifier set on the router's own `.navigationTitle` view does nothing: the chat stack owns the window toolbar. With the title gone the window search item follows the title slot and jumped to the leading edge of the detail toolbar (seen in the hosted window, pinned red by `testSearchItemStaysTrailingOnBotsCronAndKanban`), so the same stack's toolbar adds `MacPaneToolbarFill` on the non-chat routes: a `ToolbarSpacer(.flexible)` that takes the slack, leaving the item at the trailing edge exactly as on the chat route (same maxX), the toolbar still and nothing in overflow, also across live route changes. Ruling: both are gated to macOS 26 and later, because they were verified only there (this host is macOS 27). Below 26 the 0.1.3 behavior stays exactly: the pane title shows and there is no filler. (An empty flexible `.principal` item as a pre-26 filler was rejected: D11 shows a principal item takes its ideal width, not the free space; a blank-title fallback for macOS 14 was dropped with it.) Tripwires: `MacPaneTitleTests` (title string kept and toolbar title hidden on the three panes, follows the route, search item in the trailing half and within 40 pt of the edge on all three panes and across route changes, chat unchanged, the pre-26 layout test that runs on 14 to 25, RootView source pin), `MacChatRouteTests`, and `MacToolbarRealWindowTests`, whose chat stand-in applies the modifier with `false` (no flicker or width change on the chat route). The hosted stand-in mirrors the structure of RootView's chat stack, not its real items or status dot, so the two RootView lines are also pinned by whitespace-sensitive source strings.

## D7: Mac button chrome, hover outline shape, tab strip (2026-10-13)
Root cause of the "square corners behind rounded glass" (Workspace, Settings, Kanban Refresh and +): a Button left on the default Mac style draws a bordered bezel and padding under `glassEffect`. `conduitGlassControl` is applied outside the Button, so the bezel stays. Measured with ImageRenderer and the accessibility tree: default-style 44 pt glyph button reports 68 x 52, `.buttonStyle(.plain)` reports 44 x 44. The same cause gave the Kanban header its mixed heights: a Menu on the default Mac style is a 28 pt (24 pt AX) pop-up that ignores the label's 36 pt frame, a default Button is the label plus a bezel (44 pt), and `New Chat`, voice, more and folder were already `.plain`, so they were fine. Fix, one place: on macOS `conduitGlassControl` applies `.buttonStyle(.plain)` and declares `.contentShape(.accessibility, RoundedRectangle(cornerRadius))` before the glass, so every glass Button and Menu draws only the rounded shape and reports it. iOS keeps its code path.
Control heights (`MacControlHeight`, ConduitMac/Views/MacControlMetrics.swift), as of the density pass (2026-10-14; was 36 / 44): `regular` 36 is only what the macOS 27 toolbar platter measures (window-toolbar items, `toolbarItem`); `compact` 32 is every control drawn inside the window: Workspace button, Settings, New Chat, voice, more, folder, the tab strip container, the Kanban pane-header buttons, the Kanban and Cron search pills (were 40 pt) and the `MacPaneHeader` row. The 44 pt `large` is gone: it was upstream's iPad touch target. Proportions live in `MacSidebarMetrics`: 13 pt glyphs, control radius 12, row gap 6 (upstream 10), stack gap 10 (upstream 16), filter chips 24 pt tall with 9 pt padding (were 27 / 11), 22 pt Workspace avatar, session cards 24 pt icon, 10 x 5 pt padding, radius 12, 2 pt list inset, a 44 pt pitch (a 40 pt card plus the inset; was 56 pt measured in a 340 pt column; accepted in place of the ~52 pt first asked for, as closer to native Mac density), and the keyboard cursor ring follows the card radius. Hit targets stay at or above 24 pt (chips 24, tab segments 26). The workspace name is one line so the row keeps its height. New Chat was shorter only because it was sized by `padding(.vertical, 10)`.
New Chat dimming: not a rendering fault. The button is `.disabled(turnState == .synchronizing || offlineChatPresentation != nil)` with an explicit 0.6 opacity on top of the system's disabled dimming, so a gateway sync or a saved offline copy shows it washed out. Rendered enabled it is full strength (verified in both appearances). Unchanged.
Tab strip: `MacSidebarTabStrip` replaces upstream's `tabBar` on Mac. A glass container (radius 12, height 32 = `MacControlHeight.compact`; was radius 18, height 44) holds equal-width segments (`EqualWidthHStack`, no gaps); each segment is a plain Button whose own frame is the indicator: 26 pt tall, 3 pt inside the segment on all sides (was 36 pt, 4 pt), radius 9 (container minus inset, i.e. concentric), icon and name centred. Names show at the default 340 pt column (ideal 308 pt) and the strip drops to icons together when they do not fit, as before.
Window toolbar (chat): from macOS 26 every toolbar item sits on a system glass platter (`NSToolbarPlatterView`, 36 pt). Upstream also wrapped Refresh and the status dot in `conduitGlassControl` and the title in `conduitGlassSurface`, a second glass layer (the doubled outline) at 40 pt. On Mac the controls are plain content on the system platter, so Refresh, status and the title pill share the platter's 36 pt. The pill is `MacToolbarTitlePill`: flat text, 12 pt side padding, a flat fill instead of a platter before macOS 26. Menu (Rename/Delete, primary action scroll-to-top) and accessibility label are unchanged. Other views that put `conduitGlassControl` in a toolbar (group chat, Kanban sheets) are not changed.
Hover outline shape (item 2). Options: (a) radius heuristic from the AX frame alone; (b) a custom registry (marker NSView) that controls declare into; (c) read the shape the control already reports. Chosen: (c) with (a) as the fallback. SwiftUI AX nodes answer `accessibilityPath` (NSBezierPath, screen coordinates) with the shape SwiftUI uses for the control: the glass or background shape, or what `.contentShape(.accessibility, _)` / `.contentShape(_)` declares. `HoverAccessibilityEngine` reads it dynamically (`axValue`, same pattern as D5, nothing in the headers; verified present on macOS 27, rectangle = 6 path elements, rounded = 19) and `HoverOutlineShape.make` keeps it only when its bounds match the AX frame within 1.5 pt. Otherwise (AppKit controls, missing selector) the outline is a rounded rectangle with radius `min(shorter side / 2, 18)`, capped so a 44 pt button gets 18, not a 22 pt capsule. A control therefore declares its outline with the public `contentShape(.accessibility, shape)`; no registry, no marker views, nothing to keep in sync. The outline is drawn as the path itself: 10% accent wash, 1 pt accent stroke at 70%, a soft accent glow (blur 6, window outset 8). Accent is `NSColor(Color.conduitAccent)` resolved against the parent window's appearance, never `controlAccentColor`. Fallback if Apple removes `accessibilityPath`: outlines become the heuristic rounded rectangle, nothing else changes. Caveat found while measuring: a plain SwiftUI button's AX frame hugs its glyph or text (a 44 pt `Image` button reported 17 x 17) unless its label has a background or a content shape; every glass control now declares one.
Toolbar outline (fix, 2026-10-13). Evidence (live app AX tree, and the same chat toolbar hosted in a test window on macOS 27): a window-toolbar control is reported by its AppKit `NSToolbarItemViewer`, not by the SwiftUI button. Refresh is 40 x 52 (the toolbar's full 52 pt height, plus 4 pt of item spacing on one side), the status button 44 x 52 live, and the title pill's SwiftUI menu node only its text (133.5 x 14, with a sharp 6-element rectangle path). The viewer is an AppKit element, so there is no `accessibilityPath` to read, and the fallback `min(shorter side / 2, 18)` gave 18 for a 40 x 52 frame: the tall rounded rectangle. The glass the user sees is a separate 36 pt `NSGlassEffectView` (inside `NSToolbarPlatterView`, under the titlebar view), one per item: 36 x 36 for Refresh and status, 157.5 x 36 for the pill, 265 x 36 for the search field, each with `cornerRadius` 18. Fix: `ToolbarPlatterGeometry` (ConduitMac/Accessibility) lists the `NSGlassEffectView`s under the window's titlebar view (public `standardWindowButton(.closeButton)?.superview`; macOS 26+), and the engine attaches the smallest platter that contains the element's centre (36 pt tall at most, at most 32 pt wider than the element, so a platter merged over two items is ignored) to the snapshot. `HoverOutlineShape.make(frame:axPath:platter:)` then outlines the platter's frame with the glass view's radius (a circle for Refresh and status, a capsule for the pill). `snapshot.frame` stays the accessibility frame, so hit testing, the 30 Hz cache and the tooltip heuristics are unchanged; elements outside the titlebar (sidebar, content, sheets) never get a platter. Rejected: `.contentShape(.accessibility, Circle())` (the toolbar item viewer, not the SwiftUI node, is what the hit test returns, so it is never read); clamping to a child frame (the pill's child is the text, 14 pt tall); skipping the outline (a shape-matched subtle outline is the stated preference). The search field: its AppKit field cell has role text field, which the policy does not treat as interactive, so it gets no outline today (verified by sweeping the strip); if it ever does, its platter is the 265 x 36 capsule. Not covered, unverified: full screen (if the toolbar is hosted in a window without the close button, no platters are found and those items keep the old frame) and macOS before 26 (no `NSGlassEffectView`).
Redundant tooltip (item 3). `HoverTooltipPolicy` suppresses the tooltip when the element shows its label: AX title, AX text value, or a static-text child equals the label (any role, case and whitespace ignored); a radio-button role (AppKit segments, tabs, radios) whose frame can hold the label is treated as showing it (symbol-backed SwiftUI nodes excepted); and `HoverTooltipPolicy.visibleLabelIdentifier`, set with `.macVisibleLabelHint()`, marks a SwiftUI control whose label is the text it draws. The hint exists because SwiftUI button nodes expose no title, value or children (probed on macOS 27), and the aspect cutoff of 1.9 cannot hold for a 70 x 36 tab (1.94 at the default column, lower narrower). It goes on the glyph inside the tab, because a SwiftUI button takes its identifier from its image; the icon-only variant carries no hint and keeps its tooltip.

## D8: Live call orb level meter (2026-10-13)
What it does: the Mac call orb (ConduitMac/Views/LiquidOrbViewTwin.swift, an MTKView over the shared `LiquidOrbRenderer`) swells with the measured audio level instead of the call phase's 0 or 1. `LiveVoiceLevelMeter` (ConduitMac/Voice/LiveVoiceLevel.swift) ticks at 30 Hz, reads a `LiveVoiceLevelFeed`, maps RMS to 0...1 and smooths it. `state` (idle, listening, speaking) still picks the colour look.
Mapping: dBFS = 20 log10(rms); -50 dB is 0, -10 dB is 1, linear between, then `pow(x, 1.4)` so quiet syllables dip further below loud ones. Smoothing is a one-pole filter per tick, 40 ms time constant rising, 200 ms falling. Level at rest and in `idle`, `connecting`, `ending` and `failed` decays to exactly 0.
Source by phase (`LiveVoiceLevelRouting`): speaking is the assistant, listening is the microphone, muted is the assistant only (the mic level never shows while muted, also when `isMicrophoneMuted` is passed with a listening phase), everything else follows nothing.
Sources:
- GPT-Live (WebRTC owns both audio units, there is no tap): `WebRTCLevelPoller` polls `RTCPeerConnection.statistics` every 50 ms, only while an orb is watching. `WebRTCLevelSampler` reads `inbound-rtp` (kind audio) for the model and `media-source` (kind audio) for the mic. RMS is `sqrt(d totalAudioEnergy / d totalSamplesDuration)` between two reports; without those it falls back to `audioLevel` times 0.5 (-6 dB, because libwebrtc's `audioLevel` is a decaying peak). The header (RTCStatisticsReport.h) types the values as NSNumber/NSString dictionaries and names no keys: the keys are the W3C stats member names, and `audioLevel`, `totalAudioEnergy`, `totalSamplesDuration`, `inbound-rtp`, `media-source` were confirmed as strings in the linked WebRTC binary. This build has no RTCAudioRenderer, so there is no track sink alternative.
- Gemini Live and Grok Live (one controller): no new `installTap`. Both audio kinds (default capture + playback services, and `EchoCancellingLiveVoiceAudio`) hand PCM16 across `GeminiLiveAudioInput.onChunk` and `GeminiLiveAudioOutput.play`, so `LiveVoiceMeteredAudioInput/Output` wrap those two seams in the controller's `init` (Mac only) and compute RMS there, on the main actor where the chunks already arrive. That sidesteps the double-tap exception and the format-mismatch hazards in VoiceAudioEngineRecovery entirely: nothing touches an AVAudioEngine bus. Model speech arrives faster than it plays, so its RMS windows (20 ms) are laid on a playback timeline (a chunk starts when the previous ends, or now) and read at the current time; `interrupt` clears the timeline.
Threading: no audio render thread is involved. The feed is a few scalars and one small array behind an `OSAllocatedUnfairLock` (Synchronization.Atomic needs macOS 15, the target is 14); writers are the main actor and WebRTC's statistics callback, the reader is the 30 Hz main-actor tick. An RMS older than 0.3 s is silence.
Orb: `LiquidOrbRenderer.speechIsMeasured` (Mac only) follows the level at rate 20/s (about 50 ms) instead of the 4/s ease built for the 0/1 step, so the meter's own attack and release are not smoothed twice, and builds the bands from the level (`LiquidOrbAudio.measured`). The renderer's existing `apply`/`applyPulse` do the shader work (speed, warp, sheen, exposure and up to 8% sphere swell); no shader uniform beyond those is touched. Until the routed source has reported (or if a provider cannot measure) the orb keeps the phase's 0 or 1.
Frame rate: 60 fps only while the level is above 0.02 (back to 30 under 0.012), 30 in Low Power Mode, a still frame under Reduce Motion, the user's setting or thermal serious/critical (`LiveVoiceOrbPower.animates`). The view also pauses while its window is occluded. The meter and the polling stop while the orb does not animate or its window does not show: `LiquidOrbMTKView` reports `isWindowVisible` changes (occlusion, minimise, no window), `MacLiquidOrbLevelView` runs the meter only while `animates && visible` (and `onDisappear` stops it), and `stop()` zeroes the level so a return shows no stale value. The meter holds a watcher count on the feed; the WebRTC poller starts and cancels its 50 ms loop from the feed's watch signal (no wakeups while unwatched, sampler reset on resume, a lost stats handler frees itself after 1 s), and the Gemini/Grok seam wrappers skip measuring while nobody watches. A meter deallocated while running releases its watch. A mute (microphone handing over to the assistant) clears the mic's smoothing tail at once; ending the call still decays.
Not verifiable without a call: the WebRTC statistics keys at runtime (values and whether `media-source` reports while the track is disabled), playback timing offset for Gemini/Grok (no output latency compensation), and how the swell feels on real speech.

## D9: Return sends on Mac (2026-10-14)
Upstream's "Return key sends" (`ComposerReturnKey.preferenceKey`, Settings > Keyboard) is opt-in because iOS assumes the on-screen keyboard. Every Mac has a hardware keyboard, so `MacDefaults.register()` registers it as `true`. It is a registered default, not a stored value, so turning the setting off still wins. Shift-Return and Option-Return insert a new line (`ComposerTextView.isNewlineModifier`). The upstream policy is unchanged: Return never sends during IME composition, and never acts as Stop. Known wording gap: the Keyboard section's copy still mentions the on-screen keyboard (upstream file, left as is).

## D10: Keyboard support (2026-10-14)
Shortcut table (menus in ConduitCommands; one definition each, guarded by MacKeyboardMenuTests):

| Cmd-[ and Cmd-] | Go > Previous Session / Next Session | opens the neighbour in the sidebar's displayed order |
| Opt-Cmd-Up / Opt-Cmd-Down | Go > Session Above / Session Below | same two commands (a menu item has one key equivalent, so a second item, titled by direction) |

| Tab / Shift-Tab | (list or composer focused) | next / previous view in the window's key view loop (Shift-Tab is the back-tab character U+0019, handled separately) |

The Go and Search actions do nothing while a sheet is attached to the key window or is the key window (Cmd-] would otherwise open a session behind the model picker). The guard runs inside the actions, not as `.disabled` on the items: the menu is not rebuilt when a sheet opens or closes, and a stale disabled item still swallows its key (AppKit stops at the first match), so the items are never disabled for a sheet. (Previous / Next are disabled at the list ends, which is live state.) Cmd-L with no window to address does nothing rather than reach every composer.

Previous / next order: the list publishes the ids it renders, top to bottom (pinned, then recent; in the Projects view its pinned section), as a focused scene value (`macSessionOrder`), so the order, the source / status chips and the search text are exactly what the user sees. Open goes through `requestOpenSession`, the call a row click makes, so the route returns to chat. No wrap: at either end the item is disabled (no-op). With no list mounted it is disabled. If the open session is not listed (hidden by the search or a chip), Next enters at the top and Previous at the bottom. Saved offline rows are not part of the order. The sidebar column stays mounted when collapsed (probed: no `onDisappear`), so the commands also work with the sidebar hidden.

Cmd-F and Find. Superseded in part by D23: the contextual item is now 'Find in Chat' and a focused message view opens whole-chat find instead of its own bar; the placement reasoning below still holds. TextEditingCommands adds Edit > Find > Find... on Cmd-F. AppKit's menu key matching stops at the first item with the key equivalent even when that item is disabled (probed with a two-item NSMenu: a disabled first item swallows the key, the enabled second one never fires), and Find is disabled unless a find-capable text view is first responder (the composer is not: `usesFindPanel` false). So there is one Cmd-F item, "Search Sessions", placed in Edit after the pasteboard group (`CommandGroup(after: .pasteboard)`), ahead of the Find submenu; SwiftUI then drops the Find item's own key equivalent (asserted in MacKeyboardMenuTests). The item is contextual (`MacKeyboardActions.findOrSearchSessions`): when chat is the shown pane (`MacChatRoute.isChatActive`: the hidden chat under Bots / Cron / Kanban can keep a message view as first responder, and its find bar would be invisible) and the first responder is an on-screen `NSTextView` (in a visible window, not hidden or under a hidden ancestor) with `usesFindBar` or `usesFindPanel` that validates the Find action (message text, `SelectableTextView`), it sends `performFindPanelAction` (show find interface) to it, so per-message find keeps Cmd-F; otherwise it focuses Search Sessions. Both branches, the non-chat route and the off-screen view are tested. Edit > Find > Find... remains in the menu for the mouse, and Find Next (Cmd-G) works once a bar is open. Transcript-wide find is still deferred. "Switching to Sessions first": the sidebar always lists sessions on Mac (D6), so Cmd-F does not touch the main pane; the Sessions tab matters only to Cmd-L.

Cmd-[ / Cmd-] and the text system. Menu key equivalents run before any text view sees the key, and `ComposerTextView` / NSTextView answer `performKeyEquivalent` false for all nine shortcuts (asserted); nothing in the standard key bindings is on them in a plain-text composer.

Cmd-L and route-held focus. The command writes the Sessions tab, then posts `macFocusComposerRequested` with the key window. The composer's coordinator (it replaces its observer if it is ever asked to observe again) takes first responder in that window (`ComposerTextView.focusFromCommand`: editable, not hidden, no attached sheet) and clears any held focus. `restoreFocusIfHeld` and `resignForRoute` are untouched; the end-to-end test holds focus under Kanban, runs the command and checks focus stays after the route update lands.

Item 4, the session list. SessionList is a `List` (NSTableView-backed `SwiftUIOutlineListView`) of plain Buttons with no selection binding, and `.searchable` on the List puts "Search sessions" in the window toolbar. Chosen: keep the List as is and append one modifier (`MacSessionListKeyboard`) that adds a cursor: `onKeyPress` on Up / Down / Home / End / Return / Tab, `@FocusState` (`.focused`) to know the list has the keyboard, a `ScrollViewReader` to scroll the cursor row in, an overlay ring on the row (`MacSessionCursorRow`, accent stroke 2 pt plus 10% fill, `Color.conduitAccent` is adaptive; a render test compares the ring against the row without it in light and dark, change over 60/255). The ring shows only while the list is focused, starts from the open session, and appears at once only when focus arrives by key (Tab), not by click. Up/Down never wrap. Modified arrows (Shift, Option, Command, Control) are ignored. Arrow keys arrive with the numeric-pad and function flags, so "no modifiers" tests only shift/control/option/command (found the hard way: a plain `modifiers.isEmpty` guard never matched).
Tab and the key view loop. Shift-Tab on a real keyboard is the back-tab character U+0019 with the Shift flag, which `onKeyPress(.tab)` does not match, so the list has a second `onKeyPress(characters:)` handler for it (tested with that exact event; the first version handled only Tab plus Shift and never ran). The window's loop already holds the sidebar list, the toolbar search field and the composer (probed with `selectNextKeyView`). Two things stopped Tab: the SwiftUI list consumes Tab (a Tab `keyDown` on the table never moves focus), so the modifier calls `selectNextKeyView` / `selectPreviousKeyView` on the host window; and NSTextView types a tab, so `ComposerTextView` overrides `insertTab` / `insertBacktab` to move along the loop (a literal tab can now come only from paste: Option-Tab does not type one either, it inserted a newline on macOS 27 in a plain NSTextView; fine for a send-on-Return composer, but typing indented code by hand is no longer possible). Nothing is forced: the loop contains what AppKit already lets take the keyboard, so the system "Keyboard navigation" (full keyboard access) setting still decides whether buttons are reachable. Control-Tab is left alone.
Rejected: (a) `List(selection:)`. It gives native Up/Down, highlight and scrolling, but the initialiser cannot be gated, so it needs the whole List body duplicated under `#if os(macOS)` / `#else` (about 40 lines to keep in sync) or moved into a helper (removes lines outside a gate; violates the iOS-identical rule). Probed anyway: it works with `onKeyPress(.return)`, so it is the fallback if the cursor ever needs native selection semantics (multi-select, drag). (b) `.focusable()` rows or Button-per-row focus: only reachable with Full Keyboard Access, so the default Mac setup would get no Tab / arrow navigation. (c) An AppKit NSTableView subclass or event monitor: not needed once `onKeyPress` was shown to fire on the list headlessly, and a monitor is app-wide. (d) Rewriting rows as a `ScrollView` + `LazyVStack`: loses swipe actions and the list's cell reuse. (e) A custom first-responder shim per row: the overlay approach leaves rows, swipe actions, context menus and the hover tooltip layer untouched (the ring has hit testing and accessibility off; a hosted test clicks a row through the overlay).
Cmd-F focus. macOS 15 and later: `.searchFocused` on the List (SwiftUI binding). macOS 14 (deployment target): the AppKit search field in the window toolbar (`MacToolbarSearch`, found under the frame view; verified present as `AppKitSearchToolbarItem` on macOS 27). A request made before the list is mounted is held and consumed on appear, but only for `MacFocusRequests.pendingLifetime` (1 s), so a list that mounts after login does not take the keyboard; Cmd-L cancels a pending request. A sidebar that is still opening has no field yet, so the focus is retried (`retrySearchFocus`: immediate attempt, then every 100 ms, at most 8 retries) and the retry stops as soon as the field has the keyboard, the first responder is no longer what it was at request time (a click, Cmd-L), or another request superseded it. Each retry resets the binding first, since setting an already-true `@FocusState` does nothing.
Cost note: `keyboardNavigationIDs` runs on every `SessionList` body pass. It now filters `displayedSessions` once (pinned and recent partitions of that one array) instead of evaluating `pinnedSessions` and `unpinnedSessions` separately, but it is still an extra O(n) pass beside the body's own; left as is until a profile says otherwise. The ids are compared by `onChange`, so an unchanged list republishes nothing.
Not verified live (only hosted tests with synthetic events; an inactive test app has no key window): real hardware key events through `NSApp.sendEvent`, the macOS 14 fallback, the 0.4 s reveal delay, the exact Tab order in the full window (AppKit decides it from view geometry; hosted loops showed list -> search field and composer -> list), Cmd-F with a real message view focused (tested with an NSTextView configured like `SelectableTextView`), a click that focuses the list while the ring decides on `NSApp.currentEvent` (the ring is meant to appear only for key-initiated focus), and the macOS 14 inline-prediction Tab accept in the composer.

## D11: Mac session tabs (2026-10-14)
Spec: docs/superpowers/specs/2026-10-14-mac-session-tabs-design.md. A scrollable strip of session tabs replaces the chat toolbar's title pill (RootView principal item, one gate). Every session open adds a tab; tabs persist per dashboard and profile (conduit.mac.sessionTabs.<dashboard>.<profile>); a tab is removed only on delete (detected from sessionMutationID plus the catalog, no AppState edit); a failed open marks the tab unavailable. Closing the last tab starts a new chat unless it is already empty. Shortcuts: Cmd-1..8 tab N, Cmd-9 last, Ctrl-Tab / Cmd-Shift-] next, Ctrl-Shift-Tab / Cmd-Shift-[ previous (wrap), Cmd-W close (other windows close as usual), Cmd-Shift-T reopen (last 10). Panes moved from Cmd-1..4 to Ctrl-Cmd-1..4. Components: MacSessionTabsModel (pure), MacSessionTabsStore, MacSessionTabStrip, MacSessionTabsActions. Out of scope: reorder, rooms as tabs, sync between Macs.

Toolbar placement: the strip sits in the principal toolbar slot, which does not grow by itself: the slot gives an item its ideal width, and an ideal wider than the room moves trailing items (and the strip itself) to the overflow menu. So the strip's ideal width is a pure function of the window: `MacToolbarSlot.idealWidth(windowWidth:sidebarWidth:)` is the window width less the space left of the strip (sidebar column plus 212 pt of toggle and title area; 300 pt of traffic lights and system toggle when the sidebar is hidden) less a 156 pt trailing reserve (Refresh, the status dot and the window search item at its smallest, two 8 pt gaps, an 8 pt edge inset and a 24 pt margin), never below `minWidth` 120 pt. `MacToolbarSlotReader` only watches the window and split-view sizes: a narrower room is applied inside the resize (the toolbar lays out before the next run-loop turn, and a stale wide ideal would push the strip itself into overflow, where its width is no longer read), a wider room one turn later. Nothing about the toolbar's own layout (platter positions, visible items, the search field's width) is read, so there is no feedback and nothing to oscillate. The constants (212, 300, the 36 pt platters, 8 pt gaps and inset, 24 pt margin) were measured in the hosted harness on macOS 27 and are re-checked on each macOS release: `testStripFillsTheToolbarGapWithoutPushingItemsIntoOverflow`, `testToolbarKeepsAllItemsThroughResizeAndSidebarToggle` and `testToolbarStaysWholeAndSteadyAtTheSidebarMaximum` are the tripwire (they also assert the strip platter equals the ideal width), and a failure after an OS update means re-measure. Cost: unused room when fewer trailing items show (before the status dot appears, or with no search item); the title-area text, if any, is not measured. Limits, tested in `testAnExtraWideTrailingItemOverflowsButNothingFlickers`: a fourth trailing item, or a search field that will not squeeze to a magnifier, does not fit the reserve and pushes an item into overflow; the strip does not give way and the toolbar stays steady. Clicking the search item expands its field (about 240 pt) and has the same effect while it is focused (a known gap, not part of the flicker); the strip's width does not change because of it. With the 390 pt sidebar at the 820 pt window minimum the detail column (430 pt) cannot hold the toggle, a 120 pt strip and the reserve, so an item goes to overflow whatever the strip does (the toolbar is still steady there; `MacSidebarState.windowMinWidth` is the thing to revisit if that matters). The earlier 360 pt fallback and the "64-77% of the gap" figure are gone.

Toolbar flicker fix (0.1.1, 2026-10-14): released 0.1.1 made the connection status dot pop in and out. The first version of the reader measured the trailing platters and sized the strip to the left edge of the second platter from the right, assuming the trailing items were exactly Refresh and the status dot. The live toolbar has three: Refresh, the status dot and the window search item that `.searchable` on the sidebar session list puts there (a magnifier once squeezed). The two rightmost were then status and search, so the strip grew over Refresh's room, the toolbar pushed the status dot into the overflow menu, the two rightmost became Refresh and search, the strip shrank, the dot fit again, and the loop repeated. The hosted harness had only the toggle, the strip, Refresh and status, so it passed. The harness now carries `.searchable` on its sidebar column and asserts on the toolbar's own item list (`items` against `visibleItems`), not on a platter count. A first fix (nearest trailing platter plus a probation governor that undid growths losing an item) was reviewed and rejected: one stale measurement cleared the probation and the shrink-and-regrow loop came back. The shipped fix removed the feedback instead: no platter position feeds the width. In the harness, with the search item and the 340 and 390 pt sidebars, all five items stay on the toolbar and nothing changes over time at 820 (340 pt sidebar), 1000, 1200 and 1600 pt, through sidebar hide and show, and as the search item comes and goes. Smoke: "Status dot, Refresh and search stay put and do not flicker at any window width."

Flicker report on "0.1.2" (2026-10-14): a live accessibility sample of the running app (strip group 851/867/883 pt wide cycling, Refresh at x 1159/1171/1187, status dot popping in and out, window 1291 x 813, sidebar hidden) was first read as the 0.1.2 reader finding the wrong `NSSplitView` (its "sidebar width" of 40 to 72 pt would fit the cycling widths) and feeding the toolbar's layout back into the strip. Disproved: (1) the sampled process was 0.1.1 (`CFBundleVersion` 2, started 10:44 from the mounted `/Volumes/Conduit` image; `/Applications/Conduit.app` was 0.1.2 but not running), and `mac-v0.1.1` does not contain the feedback-free width; (2) the same window shape hosted against the 0.1.1 code reproduces the sample number for number (strip platter 847/863/879, i.e. the AX group less 4; Refresh 1159/1171/1187; the status dot in the overflow menu on and off), while the current code holds the strip at 835 pt, Refresh at 1159, the dot at 1203 and search at 1247, all five items on the toolbar, for the whole second sampled; (3) in a window shaped like the app's (`NSHostingView` content view, `[.titled, .closable, .miniaturizable, .resizable, .fullSizeContentView]`, automatic toolbar style, `.searchable` sidebar) there is exactly one `NSSplitView` under the theme frame, the navigation split (arranged subviews 340 and 1291 wide, the sidebar first; the detail wrapper spans the window under the floating sidebar), so `sidebarWidth(in:)` reads the sidebar (340) or zero when it is collapsed, and it does not change with the strip's width. The sidebar column width does not respond to the strip's ideal width, so no second coupling was found. The planned replacement (the detail column's width from `onGeometryChange`) was not adopted: with the sidebar shown the detail content is the window less the sidebar (951 of 1291 pt, leading safe area 340), but in 2 of 9 hosted runs the readout stayed at 430 x 48 (the detail minimum, leading inset 125) and never updated, so it is not a safe input. What the old hosted harness lacked is now covered by `MacToolbarRealWindowTests`: the `WindowGroup` window shape, which adds the system toggle and a split-view separator item (the `NSHostingController` harness has neither), a sidebar hidden at launch (the user's saved state), and 1291 pt. It is red against the 0.1.1 code (62 failures across both stability tests) and green on the current code. The shared sampling (`ToolbarStability`) now ignores split-view separator items. Known gap, not the flicker: a window created wider than the screen with the sidebar hidden (AppKit pulls it back inside the screen as it is shown, 1600 to 1512 pt on this Mac) can settle with the strip, Refresh and the status dot in the overflow menu and the search field expanded; the strip joins the window while the sidebar still reads as shown (804 pt), grows to 1056 pt a turn later, and the toolbar overflows it and does not recover. The same window created at 1512 pt, or unconstrained at 1600 to 2200 pt, is fine. The test windows are unconstrained so the widths do not depend on the machine's display.

Active tab text is appearance-adaptive, a deliberate deviation from the spec's "dark text": white in light mode (black at 85% on the dark-brown accent is 3.4:1; white is 5.6:1) and black at 85% in dark mode (on the light amber). `testActiveTabTextHasAtLeast4_5ToOneContrastInLightAndDark` reads rendered pixels and requires 4.5:1 in both appearances.

Group rooms (ruling): the strip is hidden while a group room is open, because the existing RootView gate (`activeRoomSurface == nil`) gives the room the toolbar; the spec's "strip stays visible, no tab selected" is dropped. The same holds under Bots, Cron and Kanban, where the chat toolbar items are absent (D6). Hidden-tab fix: `MacSessionTabsStore.isChatSurfaceShowing` (set by `bind` from `MacChatRoute.isChatActive` plus `activeRoomSurface == nil`) makes Cmd-1..9 and Ctrl-Tab to the active tab call `openSession` when the chat is not showing (`requestOpenSession` returns the pane to chat and closes a room), so the tab you asked for always appears; Cmd-W does nothing then, since the tab it would close is invisible. Bot Chats keep tabs: a bot tab reopens through the plain `requestOpenSession` path (smoke step). The deletion detector watches the cron list as well as the sessions list, so a deleted cron run loses its tab.

Window tabbing (ruling): `NSWindow.allowsAutomaticWindowTabbing = false` is set in `MacDefaults.register()` at launch. In-app tabs replace window tabs, and AppKit's Window-menu "Show Next / Previous Tab" items would compete for Ctrl-Tab and Ctrl-Shift-Tab. `AppShellTests.testAutomaticWindowTabbingIsOff` pins it. There is no keyboard way to close the window itself, since Cmd-W is Close Tab (the red close button still works).

Menu forms: AppKit reports Cmd-Shift-] as key "]" with [.shift, .command] (and Cmd-Shift-[ as "[" the same way), pinned in MacKeyboardMenuTests. Cmd-W is "Close Tab" in File, ahead of File > Close; in any window whose identifier lacks the `conduit-primary` prefix (the WindowGroup's windows are `conduit-primary-AppWindow-N`) it performs that window's ordinary close. The tab items are never `.disabled` (see D10: a stale disabled item swallows its key); the actions check the window and sheets when they run. With no tabs, or under a sheet, Cmd-1..9 and Cmd-Shift-T are consumed with no effect; Cmd-W under a sheet (or in the sheet itself) does nothing too, since Esc closes sheets (the PORTING_LEDGER R21 row for `ConduitSheetHeader`, `.keyboardShortcut(.cancelAction)`, with the fallback monitor in `ConduitMac/Accessibility/SheetEscape.swift`).

## D13: Message text views use TextKit 1 (2026-10-14)
Bug (builds 0.1.0 to 0.1.2): the last line of an assistant message was drawn partly outside its frame, so the message action row cut it off. Cause: `SelectableTextView.sizeThatFits` measures with an `NSLayoutManager` (TextKit 1, `measuredHeight`), but `NSTextView(frame:)` is TextKit 2 on macOS 13+, which lays the same text out taller. The gap is small at each paragraph break (the blank "\n\n" paragraph between blocks, plus the 4 pt line spacing) and accumulates: 4 to 5 pt for a three-paragraph reply at 600 to 1100 pt wide, 11 to 16 pt for a nine-paragraph one, and the ink of the last line ends 2 to 5 pt below the measured frame (probed with rendered pixels). Rejected causes: width mismatch (frame width equals the proposal; re-measuring at the frame width gives the same height), the markdown block splitter (plain-flow messages are one `SelectableTextView`), an outer clip (the frame itself was short).

Fix: `makeTextView` creates the view with `NSTextView(usingTextLayoutManager: false)`, so measuring and drawing share one engine and one set of line metrics. Chosen over measuring with TextKit 2 because it is a one-line change inside the Mac twin, keeps `measuredHeight` (and its callers and tests) as is, and agrees with the upstream code the Mac build compiles, which reads `textView.layoutManager` (`MarkdownSelectionCoordinator`; it is not wired to Mac text views today, selection is native); touching `.layoutManager` on a TextKit 2 view silently converts it to TextKit 1 mid-life, which would change its height after the fact if that ever changed. Measuring with `NSTextLayoutManager` would need an off-screen text view per measurement, and its `usageBoundsForTextContainer` is only valid after layout. Find (`usesFindBar`), link routing through the coordinator, native selection and accessibility are engine-independent for a plain `NSTextView` and are pinned by `SelectableTextClipTests`. Tripwire: `SelectableTextClipTests` hosts the real `MarkdownText` at 600, 760, 900 and 1100 pt (and all five chat text sizes) and asserts the frame covers the live engine's laid-out height; it also asserts the engine is TextKit 1. Moving to TextKit 2 later means changing `measuredHeight` in the same commit.

## D14: Forms use the grouped style (2026-10-14)
Bug (0.1.3, Kanban > New task): every SwiftUI `Form` in the shared views rendered in macOS's default `.columns` style, because nothing set `.formStyle`. Section headers floated as plain labels in the value column and the next header ran straight into the previous footer ("...so no worker claims it." above "Execution"); the Model / Skills / Depends on rows (Buttons with an `HStack { title; Spacer(); value; chevron }` label) drew as accent-tinted bordered slabs; the description `TextEditor` had no border, label or placeholder (a black void under Title); the sheet took the Form's small ideal size, so content touched and clipped at the right edge. Before/after pictures come from `FormShotsTests` (real offscreen window, `TEST_RUNNER_CONDUIT_FORM_SHOTS=1`).

Planned fix: one `.formStyle(.grouped)` at the app root (`ConduitMacApp.rootContent`). Finding: it does not reach a sheet. Probed on macOS 27 in a real window: a `Form` in a window under `.formStyle(.grouped)` is backed by a scroll view (`HostingScrollView`, the card list); the same style set on the presenter, above `.sheet`, or on the view carrying `.sheet`, leaves the sheet's Form as `.columns` (no scroll view), and a sheet opened from a sheet is the same. `.environmentObject` and `.tint` do reach sheets, `formStyle` does not. A style set inside each sheet would be an edit in every upstream Form view.

Fix: `ConduitMac/Compat/App/FormShim.swift` defines an app-module `Form` that wraps `SwiftUI.Form` and applies `.formStyle(.grouped)`. App-module types shadow imported ones (the same mechanism as the other Compat/App shims), and every upstream call is `Form { ... }`, so no upstream line changes. It covers sheets, sheets in sheets and non-sheet Forms alike. Mac-only helpers in `ConduitMac/Views/MacFormChrome.swift`, called from `#if os(macOS) // MAC:` regions (ledger rows): `MacFormNavigationRowStyle` / `.buttonStyle(.macFormNavigationRow)` (plain full-width row; the hit shape is applied to the label inside the style, because a `contentShape` outside the Button left the Spacer zone dead, which the first version did), `macFormEditor(text:prompt:)` (bordered `TextEditor` with a localized prompt; composer description, board description, bot personality, new-project idea) and `macFormSheetSize()` (min 520 x 480, ideal 560 x 760 clamped to the main screen's visible height less 120 pt so it never opens taller than the display; composer only). The shim also carries a `formStyle(_:)` method so an explicit style on a shared Form wins over the grouped default (none is set upstream today). On Mac the grouped style shows a section header and a same-named row label for the pickers in the filter sheet (Assignee, Tenant) and the board editor (Project, Default Workspace), so those pickers use `.labelsHidden()` (their accessibility labels stay).

Known limit: the offscreen test window cannot become the active window, so accent-tinted controls draw grey in the pictures; the slab-versus-row difference is the shape and fill, not the colour. Left alone: the other Form sheets (filters, orchestration, routing, rename, custom headers, bulk priority, new project) only get the grouped style, with no size change; they looked fine in the shots that could be taken. Task detail's shot is blank (its body is a scroll view of SwiftUI content the offscreen capture drops).

Tripwires: `MacFormStyleTests.testAppFormIsGroupedInAWindow`, `testAppFormIsGroupedInASheet`, `testAppFormIsGroupedInASheetOpenedFromASheet` (removing the shim fails the target's build, and without it the sheet Form is `.columns`); `testFormStyleSetAboveASheetDoesNotReachIt` documents the finding and goes red on a macOS where a root style does reach sheets (then the shim can go); `testAnExplicitFormStyleOnTheShimWins`; `MacComposerSheetTests.testClickingTheSpacerOfTheModelSkillsAndDependsRowsOpensThePicker` (a synthetic click 45% across each row opens its picker; red against the outside-the-Button content shape), `testDescriptionPromptShowsWhileEmptyAndGoesAfterTyping`, `testComposerSheetGeometry` (sheet at least 520 wide, Model and Skills rows span the sheet, description editor 80 to 140 pt, header above its rows, nothing past the right edge).

## D17: Ask About Window (2026-10-15)
Plan: docs/superpowers/plans/2026-10-15-mac-ask-about-window.md. ## D19 System integration: Spotlight (2026-10-15)
Spec: docs/superpowers/specs/2026-10-15-mac-system-integration-design.md, Part 2. Plan: docs/superpowers/plans/2026-10-15-mac-system-integration.md, Tasks 2.1 to 2.6. Mac only; iOS is unchanged.

Rulings (approved defaults):
- Opt-in, OFF by default. Settings > On this device > "Show chats in Spotlight" (`conduit.mac.spotlight.enabled`) with a "Remove from Spotlight" button. Chat titles can hold sensitive text, so nothing is indexed until the user turns it on.
- Title, model, message count and date only (`contentDescription` is "<model> . N messages", `contentModificationDate` is `lastActivityAt`). Message text is never read or indexed: `SessionSummary` has none, and fetching it per chat would also put message content in Spotlight. Deferred.
- Identifier: `conduit|<dashboardKey>|<percent-encoded profile>|<session id>`, domain `conduit|<dashboardKey>|<percent-encoded profile>`. `dashboardKey` is the dashboard UUID or `none`. Parsed with at most three splits on `|`, so the session id (last, unencoded) may hold dots, pipes, spaces or emoji, and a profile with odd characters round-trips. Dots were rejected: `CSSearchableItem.h` documents period-separated domains only for mail, and session ids are opaque tokens.
- Deindex on: delete (a session mutation that ends with the row in neither the live nor the archived list, via `MacSessionDeletionDetector`), archive (the row moves to `archivedSessions`, observed through `$archivedSessions`), profile switch and dashboard switch (one `deleteSearchableItems(withDomainIdentifiers:)` for the outgoing scope), toggle off (`deleteAllSearchableItems`) and the "Remove from Spotlight" button.
- A session missing from the loaded page is NEVER treated as deleted. The catalog is paged and a refresh can drop rows; absence changes nothing in the index.
- Bot chats (absent from `activeProfileSessions`), cron runs, voice job rows and archived rows are not indexed. Cap 1,000 items per scope, newest first; when later pages push the snapshot over the cap the oldest indexed rows are evicted from Spotlight (the plan only capped each run).
- Diff-based: a per-scope snapshot (`conduit.mac.spotlight.<dashboardKey>.<profile>`: id -> title and activity) means only changed rows are re-sent. Toggle off clears every snapshot key (not just the current scope's) so a later toggle on refills the emptied index instead of trusting a stale snapshot. A chat whose primary id changed (the old id is now in `alternateIds`) has its old Spotlight item removed so one chat never has two results.
- Debounce 2 s off `$sessions`. Scope (dashboard UUID and profile) comes from `$activeProfile` and `$savedDashboardRegistry`, the same publishers the session tabs store uses.
- Opening a result: `.onContinueUserActivity(CSSearchableItemActionType)` reads `CSSearchableItemActivityIdentifier`, parses it, and parks `.session(id:profile:)` in the app's `pendingExternalLink`, which the existing connected-then-open task hands to `openAppLink` (switches profile if needed; a deleted chat shows "That chat is no longer available."). An identifier from another dashboard opens nothing and shows "That chat belongs to a different Hermes dashboard."; a malformed one is ignored.

Verified against the macOS 27.0 SDK headers (Task 2.1): `CSSearchableItemActionType`, `CSSearchableItemActivityIdentifier`, `-[CSSearchableItem initWithUniqueIdentifier:domainIdentifier:attributeSet:]`, `-[CSSearchableIndex indexSearchableItems:completionHandler:]`, `deleteSearchableItemsWithIdentifiers:`, `deleteSearchableItemsWithDomainIdentifiers:`, `deleteAllSearchableItemsWithCompletionHandler:`, and the attribute-set properties `displayName`, `contentDescription`, `contentModificationDate`. All are macOS 10.11+. Swift spellings used compile in the build: `deleteSearchableItems(withIdentifiers:completionHandler:)`, `deleteSearchableItems(withDomainIdentifiers:completionHandler:)`, `deleteAllSearchableItems(completionHandler:)`. Completion handlers are marked `@Sendable` and log through a `nonisolated` helper. Core Spotlight needs no entitlement for this unsandboxed Developer ID build (`ConduitMac.entitlements` has no `app-sandbox`).

Cold launch: SwiftUI's `.onContinueUserActivity` may not fire when the activity launches Conduit, so there are two doors into one `MacSpotlightInbox` (`MacSpotlightContinuation.swift`): the modifier, and `ConduitMacAppDelegate.application(_:continue:restorationHandler:)` (AppKit, returns true only for `CSSearchableItemActionType`). A launch that arrives before a window attaches its handler is parked and delivered on attach; the handler runs `MacSpotlightContinuation.outcome` and parks the link in `pendingExternalLink` until Hermes connects. If both doors fire for one click, the same identifier inside 1.5 s is dropped, so the chat opens once. Whether SwiftUI still delivers after the delegate returns true is not verified (R18); the dedupe makes either answer safe.

Review round 1 changes: (a) items carry `expirationDate = .distantFuture`: Core Spotlight expires items after one month by default (`CSSearchableItem.h`), and the diff-based snapshot never re-sends an unchanged row, so idle chats would have vanished from Spotlight while the snapshot still listed them (the plan said "left at the default"); removal is explicit (delete, archive, scope, toggle). (b) Item building and every Core Spotlight call run on one serial utility queue, off the main thread. (c) A dashboard-registry publish that leaves the scope unchanged no longer cancels the pending debounced sync (it used to drop the update). (d) A row that is new this run and already older than a full index is dropped without a delete call on every pass.

Deviations from the plan: (1) the `|` identifier codec and 2 s debounce are as planned, but the debounce is a `TimeInterval` (the plan's `DispatchQueue.SchedulerTimeType.Stride` needs a conversion helper that is not needed); (2) `MacSessionDeletionDetector.mutationChanged` takes an `archived:` list, so the binder passes `appState.archivedSessions`; (3) archive is a separate path (`sessionsArchived`) because an archived row leaves `sessions` for `archivedSessions` rather than staying in the catalog flagged archived; (4) the cap evicts across pages and toggle off wipes every snapshot key; (5) `MacSpotlightBinderTests` and `MacSpotlightSettingsTests` live in their own files; (6) the decision number is D19, not the plan's D15.

Rejected: `NSUserActivity.isEligibleForSearch` per opened chat (only covers visited chats, no deindex control); a Spotlight importer plugin (needs a file store).

Limits: "Remove from Spotlight" while the toggle is on empties the index and the snapshots, so the next change to the chat list re-indexes every loaded chat (the footnote says chats are added again while the toggle is on; turn the toggle off to stay empty). The snapshot is not reconciled with the real index, so if the user rebuilds Spotlight's index the chats stay missing until "Remove from Spotlight" or a toggle cycle refills it. Older pages index as they load; the mirror never exceeds the loaded catalog.

## D19 System integration: Services and Shortcuts (2026-10-15)
Spec: docs/superpowers/specs/2026-10-15-mac-system-integration-design.md; plan: docs/superpowers/plans/2026-10-15-mac-system-integration.md (the plan and spec call this D15 and D12; D15 to D18 went to other work, so this record is D19). The Spotlight part appends its own `D19 System integration: Spotlight` section.

Services ("Send to Hermes", Part 1):
- Prefill, never send. A selection is partial, may hold secrets, and arrives from another app with no confirmation; sending would start a billed turn. The text always goes into a NEW chat (`MacNewChatPrefiller`: `createNewSession()` is awaitable, then `prefillComposer`); the active chat's draft and turn are never touched. If the create is refused (disconnected, connecting, profile switching) the active session does not change and nothing is prefilled anywhere. The routing modifiers (Services and Shortcuts) apply a parked request only when `isConnected && !isConnecting && !isProfileSwitching` (`AppState.macCanApplyParkedRequest`), because `createNewSession` refuses otherwise and the request was already taken. The prefill also refuses when the chat that is open after the create already holds a saved draft (the create awaits the gateway, so the user may have opened another chat meanwhile).
- Plain text only, trimmed, empty rejected with "No text selected" (localized), capped at 20,000 characters, longer input truncated with a trailing "[truncated]" (`MacServiceText`, shared with the New Conduit Chat intent; the cap walks at most 20,000 characters, never a full count of a huge selection). The delegate brings Conduit forward as soon as a Service arrives, connected or not, so a disconnected or backgrounded Conduit shows the connection UI the text is waiting on. Rich text is flattened by `NSPasteboard.string(forType: .string)`. No key equivalent.
- Parked until connected: `MacServiceInbox` holds one slot, last write wins, taken exactly once. Text submitted before the view installed the scope provider (a cold-launch Service) is stamped with the scope current at install. `take()` drops text whose dashboard or profile scope (`<dashboardID or none>.<profile>`) changed since it arrived, so it never leaks into another workspace.
- No URL scheme (text in a URL handler: any app could trigger it) and no share extension.
- Findings (Task 1.1): Services Info.plist shape matches TextEdit (`NSMenuItem.default`, `NSMessage` without colon, `NSPortName`, `NSSendTypes` as UTIs, no `NSReturnTypes` for a send-only service). `NSApplication.servicesProvider` is the registration point; AppKit holds it weakly, so the delegate keeps a strong reference. `NSStringPboardType` is deprecated since macOS 10.14 (use `.string`, `public.utf8-plain-text`); `NSSendTypes` is `public.utf8-plain-text` and `public.plain-text`. The app is unsandboxed (no `com.apple.security.app-sandbox`), so no entitlement is needed.
- Menu title localization: Apple apps localize Services menu titles with `<lang>.lproj/ServicesMenu.strings`. `ConduitMac/Resources/ServicesMenu.xcstrings` (a Mac-only String Catalog) compiles to that file in every shipped language (verified in the built bundle). `scripts/check-l10n-coverage.py` covers only Localizable, AppShortcuts and InfoPlist catalogs, so this catalog is NOT checked by CI; a new shipped language must add its `Send to Hermes` translation here by hand.
- macOS caches the Services list: after installing a build run `/System/Library/CoreServices/pbs -update` (and relaunch Conduit once) before the menu item appears.

Shortcuts (Part 3):
- Two Mac-only intents live in `ConduitMac/Intents/` (no iOS exposure, no ledger row for the intent files): `NewChatIntent` ("New Conduit Chat", optional Profile and Message) and `OpenSessionIntent` ("Open Conduit Chat", required Chat). `NewChatIntent` prefills, never sends (a Shortcut can be imported from anywhere; sending starts a billed turn); an unknown profile throws a readable `MacIntentError.unknownProfile` instead of creating a chat on the wrong profile. The message uses the Services normalizer (trim, 20,000 cap, "[truncated]").
- Hand-off: `perform()` enqueues a `MacIntentRequest` in `MacIntentInbox` (one slot, last write wins); `MacIntentRouting` applies it once Hermes is connected: bring the window forward, switch profile if asked (abort if the switch did not land), then `MacNewChatPrefiller` (or a bare `createNewSession()` with no message) or `appState.openAppLink(.session(...))`. Intents compiled into the app run in the app process on macOS (no extension), so the inbox set in `perform()` reaches the running app; this is the same path `StartVoiceConversationIntent` uses with `PendingVoiceIntentStore`.
- `ConduitSessionEntity` / `ConduitSessionEntityQuery` (`EntityStringQuery`) read the live catalog through `MacIntentDataSource` (weak `AppState`, bound by the routing modifier). `entities(for:)` resolves a saved id even with no catalog (the app may have just launched or the chat is on an unloaded page); opening a gone chat then reports "That chat is no longer available.". An entity resolved without the catalog has `profile == nil`, so it opens on the active profile and a chat on another profile reports unavailable. Accepted for v1.
- One `AppShortcutsProvider` per app, so the two `AppShortcut` entries are added to `ConduitVoiceShortcuts.appShortcuts` behind one `#if os(macOS) // MAC:` region (PORTING_LEDGER row). Total shortcuts: 3 (limit 10); every phrase contains `\(.applicationName)`; no parameter in any new phrase, so `updateAppShortcutParameters()` needs no new call site.
- Findings (Task 3.1): `IntentModes` and `supportedModes` are `anyAppleOS 26.0` (macOS 26), so both new intents declare `@available(macOS 26.0, *) static var supportedModes` next to a literal `openAppWhenRun = true` (deployment target is macOS 14; `openAppWhenRun` is a boolean literal because the metadata processor rejects computed values). `EntityStringQuery` and `IntentDialog` are macOS 13+. `AppShortcutsBuilder` rejects `if` except `#available`, but a `#if os(macOS)` region is resolved before the builder and compiles. An `AppShortcut` for an intent with a required, non-optional parameter that no phrase references (`OpenSessionIntent`) builds and the metadata processor lists it among `autoShortcuts` with no warning; whether Siri prompts for the chat at run time was not verified here; the entry stays in `autoShortcuts` (the build accepts it) and the smoke checklist covers the prompt (Shortcuts and Spotlight list the action regardless). The build log carries no App Intents metadata warning before or after.
- Test helper: `SessionSummary.intentTestSummary` lives in `ConduitSessionEntityTests.swift` instead of extending `macTestSummary`, so parallel work on that helper cannot conflict.
- Deferred: "Ask Hermes returns reply". It needs an AppState entry point that runs a headless turn and returns the final text, with a 120 s timeout, a disconnected error, and a "Needs approval in Conduit" failure instead of waiting on an approval prompt.

## D18: Mac command palette (2026-10-15)
Spec: docs/superpowers/specs/2026-10-15-mac-command-palette-design.md. Cmd-K (Go > Command Palette) toggles an in-window overlay: search field over a ranked list, 560 pt wide, 9 visible rows, scrim, Esc clears then closes. It only dispatches existing app actions and never sends free text as a prompt (Quick Ask owns that). Items: sessions (`activeProfileSessions`, non-archived), slash commands (`slashCommands`; routed by `MacPaletteSlashPolicy`, see Review round 1), profiles (the active one is a non-runnable check row), "Switch Model..." (opens the model picker; no inline model list), panes, New Chat, Settings, Hide/Show Sidebar, Stop Response (only while a turn runs), Search Sessions, Check for Updates. Prefix scoping `/ > @ #`.

Ranking: tiers exact > prefix > word start > substring > fuzzy (3+ chars) > keyword; kind weights; recency boost 60 decaying 6 per rank; session unread +10 and last-24h +5; disabled rows last in their tier; 50-row cap. Recents: 20 ids per dashboard and profile in `conduit.mac.palette.recents.<dashboard>.<profile>`, 8 shown; items that no longer exist drop on read (lookup), the stored list is not rewritten because the session catalog is paged. The palette closes before the action runs; focus returns to the composer if it held it.

Components (ConduitMac/Palette): MacPaletteItem, MacPaletteMatcher, MacPaletteRecents, MacPaletteProvider, MacPaletteStore (with MacPaletteCalls and MacPaletteDispatcher so tests never touch AppState), MacPaletteBinding (live calls and snapshot), MacPaletteView; `MacPaletteActions` in MacKeyboardShortcuts.swift. The overlay hangs on RootView in ConduitMacApp (`.overlay { MacPaletteView() }`), so it needs no RootView edit.

Upstream edit: one gated `.onReceive(.macOpenSettingsRequested)` in RootView (ledger row), because `settingsLinkRequest` only reaches the calls and voice pages. No AppState edit.

Key handling: the arrow, Home/End, Esc and Tab handlers are `onKeyPress` modifiers on the panel, and they receive the keys from the focused TextField (MacPaletteViewTests.testKeyEventsReachTheStore sends synthetic events to the window; so neither fallback (the modifiers on the field, an NSEvent monitor) was needed; confirm with real keys in the smoke list). Return is never a key handler: it runs through the field's `onSubmit`, so a Return that confirms an IME composition does not run the row. Esc is not intercepted by SheetEscape (that monitor acts only when the window is a sheet).

Selected-row text follows the tab rule (D11): black at 85% on the dark-mode amber, white on the light-mode brown. Menu strings follow the existing Mac menus (SwiftUI literals); palette strings are in the catalog for every shipped language.

Deviations from the plan, found while building: the overflow test needs one key press per run-loop turn (an `onChange` does not fire for selection changes made before the view exists); the empty-state label needs `accessibilityElement(children: .ignore)` to be exposed as a label; the sample query in the row test is "number" because the Sessions pane row outranks session rows for "session".

Review round 1 (2026-10-15), behaviour changes:
- Slash routing is `MacPaletteSlashPolicy`, not `argsHint` alone. The built-in catalog and the gateway `pairs` catalog carry no `argsHint`, so `/background`, `/queue` and `/steer` would have run bare and `/undo`, `/compress`, `/yolo` or any skill on one Return. Now: a known read-only or non-destructive command (new, branch, model, help, status, usage, version, agents, save, debug) runs; a command that takes an argument (`argsHint`, or background, queue, steer, goal, personality, approvals, tools, rollback) goes to the composer as `/name `; everything else (undo, retry, compress, yolo, stop, skills, plugins, unknown gateway commands) asks first. A slash command shows the chat pane first (its output and composer live there; Kanban / Bots / Cron keep the chat mounted but hidden).
- Confirmation is a second step inside the palette (no alert): the list is replaced by the question, Return confirms, Esc, typing or an arrow goes back, the palette stays open until confirmed, and a cancelled row is not a recent. It applies to Stop Response, a profile switch while a turn runs, the slash rows above, and inserting `/name ` over a typed draft.
- Draft safety: `insertSlash` fills the composer at once only when the draft is empty or blank; otherwise it asks "Replace your draft?" (attachments are kept). It never replaces typed text silently. Chosen over "fill only when empty" because that leaves the row dead while the user is typing; the confirm keeps the row usable and is just as safe. The live draft is read from the mounted `ComposerTextView` (the draft store only holds text saved on a chat change).
- Typing resets the highlight to the best row (a row carried over from the old query could sit anywhere in the new list and Return would run it); a refresh keeps it. Items, the matcher index (folded titles, words, keywords) and the id lookup are built once per open, so a keystroke only ranks (no snapshot, provider run or diacritic folding per key; 5,000 sessions, 8 keystrokes: about 0.12 s in the test). `ConduitCommands` holds the store without observing it (it published on every keystroke and rebuilt the menu bar).
- Focus: closing returns focus to whichever AppKit responder held it (composer by the Cmd-L request, otherwise the view or the text field behind the field editor), held weakly.
- Accessibility: the overlay is `isModal`; the field is a search field; arrow moves are announced (`navigationToken`, not when typing resets the highlight); unread is in the row label; non-runnable rows are `.disabled`; the confirmation heading and hint are exposed. Contrast: subtitles, reasons and headers use primary at 70% (system `.secondary` is about 3.8:1 on light) and the selected row's subtitle uses 90% of its text colour (75% was 3.9:1 on the light-mode brown); the selected unread dot takes the text colour (it was accent on accent). `MacPaletteContrastTests` computes all of them at 4.5:1 in light and dark.
- Not changed: the palette lives once per process (`MacPaletteStore.shared`) and every WindowGroup window would show it; File > New Window is removed, so there is one chat window. Session search covers the loaded catalog only.

Out of scope: inline model list, server session search, tab commands, sending prompts.

## D15: Mac Quick Ask (2026-10-15)
Spec: docs/superpowers/specs/2026-10-15-mac-quick-ask-design.md. Option-Shift-Space opens a floating panel from any app; the user types one question, the reply streams into the panel, Esc hides it, Cmd-Return opens the exchange in the main window. The panel is the shared base `MacFloatingPanelController` (non-activating, key, hides on resign key); code is under ConduitMac/QuickAsk.

Hotkey API: Carbon `RegisterEventHotKey` (`MacCarbonHotKey`, behind `MacHotKeyRegistering`) over `NSEvent` global monitors (observation only, need Accessibility) and `CGEventTap` (needs Input Monitoring). Apple DTS calls it the best of the three but legacy; no permission prompt; the combination is consumed. Fixed Option-Shift-Space: `MacQuickAskHotKey.default` is a value, the seam for a later recorder. One setting, `conduit.mac.quickAsk.enabled` (default on), as a Toggle "Quick Ask Shortcut" in the Chat menu.

Sequoia caveat: macOS 15.0 and 15.1 return -9868 (`eventInternalErr`) for Option-only and Option-Shift-only hotkeys (Apple engineer, developer.apple.com/forums/thread/763878: intentional, fixed in 15.2 beta 2). Registration failure is a visible, non-fatal state: the Chat menu shows a disabled line naming the reason (this macOS version, taken by another app, other), Chat > Quick Ask (no key equivalent, never disabled) always opens the panel, and registration is retried on app activation and when the toggle changes (no retry loop). The hotkey is never registered under XCTest.

Stream: Quick Ask subscribes to the shared base `MacStreamEventHub` (fed by the base's one gated line in `AppState.handleStreamEvent`) and runs its own pure reducer (`MacQuickAskModel`). AppState and the open chat are untouched, so a Quick Ask turn never changes the transcript in the main window. This plan makes no edit under Conduit/ or Shared/ except the string catalog. Approvals, clarify, input prompts, reasoning cards and attachments are not rebuilt in the panel: the panel says "Hermes needs your input" and makes Open in Conduit the default action.

Reducer rules: events count only for owned runtime or stored ids and only while sending, streaming or done; an event that arrives before `prompt.submit` returns is kept; `messageComplete` replaces only the current segment, and a `messageStart` after a completion keeps the turn open and joins segments with a blank line (a tool turn); `sessionBusy(false)` ends a streaming turn, never a sending one. Whether a real tool turn emits several `message.complete` segments is still unconfirmed: the fixture ConduitMacTests/Fixtures/quickask-tool-turn.jsonl is synthetic (written from the StreamEventParserTests shapes, marked FIXTURE-SYNTHETIC), not recorded. Re-record it against a live gateway and change the rules and tests together if the real trace differs.

Sessions: new session per invocation (`session.create` with no model or provider, so the profile default applies, not `runtime.model`, which mirrors the open chat's possible override). Nothing is created when the panel is dismissed without sending. Reopening within 120 s of the last activity (a hidden turn that keeps streaming counts) restores the exchange and continues the same session; Cmd-N or a longer gap opens empty. Esc, the hotkey and click-outside hide the panel and do not stop the turn; Cmd-. stops it. Quick Ask sessions are ordinary sidebar sessions (the controller refreshes the list after create). A create that returns another profile's session is rejected before it is adopted.

Promotion: Cmd-Return or Open in Conduit brings the main window forward (`MacWindowActivation.bringConduitForward`), then calls `requestOpenSession` once with the stored id (the runtime id until `session.title` or the create result supplies it), then the model detaches and the panel hides. A turn still streaming continues in the main chat through `session.resume`.

Errors: `session.create` refused with 4090 (and not `SESSION_NOT_OWNED`) shows a plain-language limit message, keeps the typed prompt, and offers Retry and Open Conduit. Any other failure keeps the prompt and offers Retry (a failed send retries on the existing session without a second create). Not connected or reconnecting disables the field and offers Open Conduit; a connection lost mid-turn cancels nothing and keeps promote available. Cmd-N while a create is in flight discards it (the late session is not adopted).

Wiring (deviation from the plan, which bound from a window `.task`): `MacQuickAskBootstrap.start` runs from `applicationDidFinishLaunching` with `AppStateRuntimeRegistry.shared.appState`, as `MacActivityBootstrap` does, so the hotkey and the hub subscription work with no window open. It installs the real panel, binds the controller and refreshes the hotkey. `applicationDidBecomeActive` retries a failed registration.

Panel focus: a freshly shown non-activating panel has the window itself as first responder, and SwiftUI cannot move `@FocusState` into the field from there (found with a hosted real-panel test). The view hands the hosting view first responder, then asks for the field, on appear and on every `show()` (`focusRequest`), and again when a turn ends.

Reconnect while Conduit is inactive depends on the shared base's Mac exemption. Out of scope for v1: attachments, slash commands, dictation, model picker, panel history, rebinding, launch at login, menu-bar item.

Review round 1 (2026-10-15), behaviour changes:
- Cmd-. and Cmd-N: the Chat > Stop Response and File > New Chat actions check `MacQuickAskController.isPanelKey` and, with the panel key, stop only the Quick Ask turn or start a new Quick Ask conversation. Which of the menu or the panel's own hidden button AppKit offers the key to first was not verified at runtime, so the routing holds either way. `MacKeyboardActions.commandsBlocked` is also true for a `MacFloatingPanel`, so tab, sidebar, search and session shortcuts do nothing from the panel.
- Stream: the controller joins the hub only while it holds a session (create result until reset or promotion), and drops events through `MacQuickAskModel.isRelevant` before touching the published model, so a delta of the main chat no longer invalidates the panel.
- Hotkey: `MacQuickAskHotKeyManager` follows the `conduit.mac.quickAsk.enabled` default itself (a menu item is not a live view, so the Toggle's onChange is not relied on) and `shutdown()` releases the hotkey and event handler at termination.
- Untrusted text: tool names, gateway error text and the profile name in the mismatch message pass through `MacUntrustedText.sanitize(_:maxGraphemes:)` (ConduitMac/Shared) before they reach the panel. The reply body renders as Markdown like the main chat.
- Promotion: `requestOpenSession` accepts a runtime id (alias lookup, identity capture and resume all tolerate it while the runtime lives); the open also maps a runtime alias to the catalog row id when the catalog lists one.

## D16: Mac notch agent status (2026-10-15)
Spec: docs/superpowers/specs/2026-10-15-mac-notch-status-design.md. Plan: docs/superpowers/plans/2026-10-15-mac-notch-status.md.

- Surface: hidden when idle; at the top-center of NSScreen.main it is wings around the notch (safeAreaInsets.top > 0 with both auxiliary areas non-empty) or a 28 pt pill elsewhere. Built on MacFloatingPanel (non-activating, non-key) driven by AgentActivityFeed. No menu bar icon, no third-party notch package.
- Window level: `.statusBar`, above the Dock. A panel docked at the bottom, left or right edge uses the full screen frame and the Dock draws above `.floating` windows, so `.floating` would hide it. Pinned by NotchPanelHostTests.
- Mode (conduit.mac.notchStatus.mode): "Active agents" (default), "Only when I'm needed", "Off". Go > Show Agent Status pins the panel open even when Off.
- Rows: Needs you (approvals, clarify, input prompts), Working, Done (30 s, max 3). Kanban blocked/review rows and the cron footer are follow-up: the shared base never produces those items, so the code path exists (fixture-tested) and v1 shows neither.
- Draggable (user scope change after the spec): the surface can sit at any point on any screen edge of any display. The shared base's panel does the drag, the 4 pt click threshold and the snap; the placement is saved per display (conduit.mac.notchStatus.dock.<CGDirectDisplayID>), restored on launch and screen changes, ignored but kept when that display is gone. Top and bottom edges open vertically inward from a horizontal capsule; left and right edges open horizontally inward from a vertical capsule; wings exist only in the default placement. Go > Reset Agent Status Position and a double-click on the capsule or grip return to the default. Nothing expands, collapses, announces or moves mid-drag; attention that arrives mid-drag applies at the drop.
- Approvals (hardened after security review, "UI approval spoofing"):
  - An approval row leads with the gateway payload: the approval description and the command (monospaced, 2 lines). The session title is a separate, secondary line. The ApprovalActivity model carries no tool name, so the payload is description plus command.
  - All gateway/agent text is sanitized once in the row builder by `MacUntrustedText` (ConduitMac/Shared, shared with Quick Ask and notifications): NFC; drop Cc, Cf, Co, Cn, Zl, Zp; ZWJ only inside emoji; whitespace collapsed; at most 2 combining marks per base; grapheme cap with an ellipsis. The views draw it with `Text(verbatim:)`, so no Markdown or link detection applies.
  - Buttons map only to fixed `NotchApprovalAction` values (labels are fixed localized strings) and choices from `AgentActivityApprovalChoices.allowed(for:)`. Allow once and Deny are inline; Allow for session and Always allow are menu-only; clarify, sudo, secret and vault prompts are never inline.
  - A command that was cut, or had hidden or control characters removed, or is empty, is not approvable inline: Allow once becomes "Review in Conduit" (opens the session), the menu is removed, Deny stays.
  - The controller never parses ids or choices from text. On a click it reads the live item back from the feed by the row's exact id and requires kind == approval, state needs-user, the same sessionKey and approval status pending, checks the choice against `allowed(for:)`, then calls `respond(to: item.id, choice:)`; the feed resolves the id.
  - 600 ms click guard after an auto-expand; no default-key binding anywhere.
- Surface is black in light and dark so it blends into the notch; text at least 4.5:1.
- Visibility limit (verified against the gateway): Conduit sees only sessions on its own socket. Sessions started by another process (CLI, Slack, a separate cron process) are invisible. Sessions of the same gateway process appear in session.active_list, but approvals and events flow only after session.activate / session.resume; opening a row from the notch does that, which adds Conduit as a viewer. The empty state, the Settings footnote and this entry say so. Esc reaches the panel only while Conduit is the active app (the panel is never key); click outside and moving the pointer away work always.
- Components: NotchGeometry, NotchLayout, NotchDockStore, NotchRowBuilder, NotchApprovalActions, NotchStatusState (pure); NotchStatusController, NotchPanelHost, NotchStatusView; MacUntrustedText (shared).

Review round 1 (2026-10-15), behaviour changes:
- Allow is bound to the exact command shown: the row carries a SHA-256 of the raw payload command (`NotchApprovalContent.commandDigest`, the same digest the notifications use; no text kept). Allow once, Allow for session and Always allow are sent only if the live item still holds a command with that digest; the check runs on the click and again inside the queued answer task, with no suspension between it and the feed call. A mismatch sends nothing, rebuilds the rows from the live items and re-arms the 600 ms click guard (an approval whose command changed under its id counts as a new decision). Deny is not bound: denying is always safe.
- A command with an interior line break (newline, CR, U+2028/2029) is not approvable inline: the single-line display would read `ls\nrm -rf ~` as one command. `MacUntrustedText.sanitizeReport(...).changed` is true for any dropped scalar and for a flattened interior line break (edge whitespace, tabs, NFC composition do not count).
- The command and description are drawn without a line limit (the spec's 2 lines held about 110 monospaced characters, less than the 160-character cap, so a clipped command could look complete next to Allow once). The panel grows to fit.
- The VoiceOver label of an approval row leads with the command; the agent-worded description is only its value.
- A drop on another display stays there (`homeDisplayID`, session only, while that display is connected and keeps its saved dock); before, the next render looked up `NSScreen.main`'s placement and moved the surface back. Reset Position clears it. After a relaunch the main display's own saved spot applies.
- Off mode leaves no timer: the done-row expiry timer is scheduled only while the mode is not Off or Show Agent Status pins the panel.
- Redraw cost: every published view-model property is assigned only on a real change, so a feed emission that changes nothing the panel shows does not re-evaluate the view.
- Keyboard: the panel never becomes key (that is what keeps focus with the frontmost app), so Tab cannot reach its buttons; VoiceOver can press them, and keyboard users answer from the main window or the notification. Known limit.
- One MacUntrustedText (union of the Quick Ask, notifications and notch rules, bounded scan, joiner cap) with `sanitizeReport`; U+2028/2029 become a space (notifications rule) and count as `changed` for approvals.

### Surface styles (2026-10-15)
The notch surface was always opaque black, which users lose against dark wallpapers. It is now a choice (Settings > On this device > Notch style), modeled on the surface styles of CodeNotch (MIT, github.com/vinzdg/codenotch) and reimplemented in Conduit's idiom. This supersedes "Surface is black in light and dark" above: black is now the `solid` style and the band beside the hardware notch.

- Styles (`NotchSurfaceStyle`, ConduitMac/Notch/NotchSurfaceStyle.swift; key `conduit.mac.notchStatus.surfaceStyle`, raw values `glass`, `darkGlass`, `solid`, `dock`, unknown reads as `glass`):
  - `glass` (default): system Liquid Glass (`.glassEffect(.regular, in: shape)`). The panel has no appearance of its own, so it follows light or dark and Clear or Tinted.
  - `darkGlass`: `.glassEffect(.clear)` over a 0.80 black wash beneath it (`NotchPalette.darkGlassDimAlpha`). Panel pinned darkAqua.
  - `solid`: the original opaque black. Pinned darkAqua.
  - `dock`: a slab of `.clear.tint(black 0.15)` glass over a 0.75 black wash (`NotchPalette.dockDimAlpha`), on the bottom, left and right edges. On the top edge (default placement and a top dock) it resolves to `darkGlass` so it stays welded to the bezel. Pinned darkAqua. Unlike CodeNotch's dock the slab is not inset from the screen edge: the panel is flush with the edge and keeps its inward-rounded corners, because an inset would change the panel size, the hit shape and the placement math (follow-up if wanted).
- Resolution (pure, tested in NotchSurfaceStyleTests): `resolved(on: layout)` (dock to darkGlass on the top edge), then `effective(glassAvailable:reduceTransparency:)` (every glass style is `solid` where `#available(macOS 26.0, *)` is false, and Reduce Transparency forces `solid`), combined as `drawn(on:glassAvailable:reduceTransparency:)`. The deployment target stays macOS 14; glass code sits behind `#available(macOS 26.0, *)` like `conduitGlassSurface` in Conduit/Theme.swift.
- Hardware notch: the resting compact surface in the wings placement (standard placement on a notch display) stays black, and the expanded panel keeps a black band across its top where it meets the hardware (`reservedTopHeight`). Everywhere else (expanded panel below the band, the pill on a display without a notch, docked edges) the drawn style is painted.
- Panel appearance: `NotchPanelHost.setPanelAppearance` sets `nil` for glass (the Mac decides) and darkAqua otherwise, including when glass falls back to solid or Reduce Transparency is on. The controller applies it when the panel is made and again when the style or the Reduce Transparency setting (`NSWorkspace.accessibilityDisplayOptionsDidChangeNotification`) changes. `NotchStatusView` pins `colorScheme` dark unless the style follows the system; the black wings band pins it dark too.
- Ink: `NotchPalette.Ink` has a dark variant (the previous whites and ambers, 4.5:1 on black) and a light variant for glass in light mode (at least 4.5:1, which also covers the 3:1 for glyphs, on near-white and mid-light glass approximations). Colours are dynamic `NSColor`s, so the window appearance and the SwiftUI `colorScheme` choose the variant. Contrast tests: NotchStatusViewTests.
- Contrast (review round 1, computed in NotchSurfaceStyleTests over a white window composited with the wash, `NotchPalette.washed(over:alpha:)`): the first wash values (0.60 and 0.40) gave the secondary ink 3.4:1 and the failure ink 2.2:1 over white. Now every ink is at least 4.5:1 there: Dark glass 6.7 to 12.6, Dock 5.6 to 10.4 (the dock slab's own 0.15 tint is not counted; it is margin). The failure ink's dark variant was lightened to (1.0, 0.65, 0.63) for this; text, secondary and attention are unchanged. Glass in dark appearance is checked against two reference tones (`darkGlassReferenceRGBs`), glass in light appearance against two light ones. All of these are approximations of what the system draws; the 0.80 and 0.75 washes still need the hardware smoke pass over a bright window and over busy text.
- Known limit: the notch panel never becomes key, so AppKit may frost `.clear` glass instead of drawing it clear (CodeNotch works around it with a private `_hasActiveAppearance` override for its dock slab; Conduit does not use private API). Frosted glass is lighter than clear glass over a dark window and blurs text behind it, which only helps readability; the cost is that Dark glass and Dock look closer to each other than the names suggest.
- Allow / Deny buttons: the system `.bordered` style ignores `.tint` on macOS and drew a neutral grey pad (measured 0.10 grey on black, 0.86 grey on light, about 1.1:1 against the surface), so the buttons were identified by label alone. `NotchActionButtonStyle` (NotchStatusRowView.swift) fills with the attention (Allow) or failure (Deny) ink of the current appearance and labels it with `NotchPalette.onAccent`: the fill is at least 3:1 against every surface and the label at least 4.5:1 against the fill (tests in NotchSurfaceStyleTests). The 600 ms click guard still disables it (dimmed), and it is still never the default key.
- Settings: the Notch style picker and its one-line explanation live in `MacNotchStatusSettingsSection`, the view the existing gated AuxiliaryViews line already shows, so there is no new upstream edit. Where glass is unavailable the picker still shows, with a note that glass needs macOS 26 (the chosen style is kept for a Mac that has it).

## D20: Mac done and approval notifications (2026-10-15)
Spec: docs/superpowers/specs/2026-10-15-mac-notifications-design.md. Plan: docs/superpowers/plans/2026-10-15-mac-notifications.md. Local notifications only (no relay/APNs; PushNotificationService is not used). Events come from AgentActivityFeed (shared base) through MacAgentActivityFeedSource into a feed-neutral MacNotificationEvent; policy (MacNotificationPolicy), coordinator (MacNotificationCoordinator), content, categories, actions, router, delegate and runtime live in ConduitMac/Notifications. The text sanitizer is ConduitMac/Shared/MacUntrustedText.swift.

Defaults: master on, 30 s threshold (10/30/60/120), permission requested on the first eligible event while Conduit is inactive, never at launch. Interruption level stays active (Focus is respected).

Approvals: choices are once/session/always/deny, built per request (smart-denied: once+deny). Approve sends once, Deny sends deny; always and session are never offered; Approve is dropped if once is absent. Approve and Deny call AgentActivityFeed.respond(to: item.id, choice:) (shared base) through MacHermesNotificationGateway: resolved and alreadyResolved (4009 / "no pending") are success, failed(_) posts "Couldn't send" (Open only). Reply calls HermesClient with an explicit session id, so the active session is never switched and no AppState or HermesClient edit exists. A disconnected gateway or a different dashboard/profile sends nothing and posts the notice; nothing is queued.

Security hardening (review findings, same branch):
- Authorization: Approve, Deny and Reply all carry authenticationRequired (a locked Mac asks for unlock first) and none uses foreground; only Open foregrounds.
- Integrity of what is approved: the approval banner has a fixed title ("Approval needed"), the body is the command from the approval payload (then its description), and the session title is only the subtitle. If the command is longer than 160 graphemes (a banner clips its body to a few lines; the body itself shows up to 300), needed any sanitizing (stripped or reordered characters, collapsed newlines) or is empty, the banner has no Approve button (Deny and Open stay) and the action handler refuses an inline Approve for it and opens Conduit instead.
- Approve is bound to the exact command shown: the payload carries a SHA-256 of the command (command_digest, no text), and Approve is sent only if the feed still holds a command with that digest under the item id (the reducer can replace an item under the same id); otherwise Conduit opens. Deny does not need the match. A payload with no kind or no profile is rejected (no default into Done/default profile). Approve, Deny and a question Reply need a loaded feed (`state.baselinePending == false`): before that an empty lookup is "not loaded", so the banner stays and the "Couldn't send" notice posts instead of silently clearing it.
- Delegate: `MacNotificationDelegate.install(on:)` keeps any delegate already in the center's slot (Sparkle may take it) and forwards every notification without a conduit_mac payload to it; it re-installs on app activation.
- Untrusted text: every agent or gateway string (titles, reply previews, question text, command, description) goes through MacUntrustedText.sanitize(_:maxGraphemes:): NFC, drop Cc/Cf/Co/Cn/Zl/Zp scalars, whitespace (including U+2028/2029) collapses to one space, ZWJ kept only between pictographs (at most 4 joiners in a row, since a joined sequence is one grapheme), at most 2 combining marks per base, grapheme cap with an ellipsis, bounded scan for huge input. One implementation at ConduitMac/Shared/MacUntrustedText.swift, shared with Quick Ask (D15); Zl/Zp become a space rather than being dropped.
- No trust in identifiers: the payload carries the feed's exact item id (userInfo item_id). On an action the handler looks that exact id up in AgentActivityFeed.items (kind approval, state needsUser), requires the same session key and a choice in AgentActivityApprovalChoices.allowed(for:), and responds with that item's id. Ids are never rebuilt from the request id or from any displayed text. A missing or stale item clears the banner and sends nothing; a mismatched session or choice is ignored. A question Reply is validated the same way and uses the request id the feed item yields (MacFeedItemID.requestID, the one shared parser).

Clicks: activate and raise the main window, open the durable session key; a notification from another dashboard or profile only activates; a cold-launch click is held until connected.
Categories: setNotificationCategories replaces the whole set and HermesCallNotifications.registerCategory also calls it (skipped on Mac). MacNotificationCategories.register reads the current set, drops only CONDUIT_* and writes the union, at first post and on app-language change. If HermesCallNotifications.registerCategory is ever enabled on Mac it must use the same merge.
Limits: events arrive push-based only for sessions this dashboard socket has attached to; sessions run by another process (a terminal Hermes, another client's session this socket never attached) never notify. A poll-only session's start time is when the feed first saw it, so its duration undercounts; a turn that ended while the socket was down (observedGap) never notifies; input prompts are not notified in v1. Reply goes straight to the gateway: the sent message shows in the local transcript when the session is next opened, and a Reply after a gateway restart fails with the notice. A question Reply sends a request-level answer (no question id) and only for one open question; a multi-select question may reject a free-text answer, which posts the notice.
Held decisions: an approval or question that fires while the user is looking at the session is held and posted when attention leaves (app deactivates, window unkeyed or covered, other pane or session).
Settings: ConduitMac/Views/MacNotificationSettingsView, inserted first in NotificationsSettingsDetail by one gated edit (ledger row). System Settings URL used: x-apple.systempreferences:com.apple.Notifications-Settings.extension (not exercised in this run; verify on the smoke machine, fallback x-apple.systempreferences:com.apple.preference.notifications).
Strings: scripts/check-l10n-coverage.py does not scan ConduitMac, but the new strings are catalogued in Conduit/Localizable.xcstrings in all 13 shipped languages (additions only) via scripts/l10n.py, so the Mac UI localises. "%lld conversations finished" is a plural key.
Plan deviations: (1) MacNotificationContent.truncated delegates to MacUntrustedText; (2) approval banner layout (fixed title, command body, session subtitle) replaces the plan's session-title-first layout; (3) the Done title uses the latest session title at post time (the plan used the event's); (4) `eventSource` events carry `itemId`.

## D23: Mac chat find (2026-10-16)
Spec: docs/superpowers/specs/2026-10-16-mac-chat-find-design.md. Cmd-F (Edit > Find in Chat) opens a find bar over the top of the chat pane in the main window; the field is an `NSSearchField` (Return next, Shift-Return previous, Esc closes; IME composition is never intercepted; Shift-Return reaches the field through `doCommandBy` as `insertNewline:` with the Shift modifier on the current event, mapped to previous), the count reads "3 of 12" (capped "5000+"), Cmd-G / Cmd-Shift-G (Edit > Find Next / Find Previous) step. The model is the loaded transcript only (`AppState.messages`; no server search exists in the client): user, assistant and partial rows as drawn, via `MacChatFindText` (the views' own parser and inline builder, so link destinations, emphasis marks, fences and table separators are not hits; list and quote markers the views draw are emitted too, and gateway media is parsed like the views when a resolver exists). Matching is literal, case- and diacritic-insensitive, non-overlapping (`MacChatFindMatcher`). A new query selects the newest hit.
Highlights are TextKit 1 temporary attributes (D13) applied by a per-window registry of mounted message views keyed by message id; the id reaches the views through one environment value set by `.macChatFindRow(id:engine:)`, the only upstream edit (one gated region, 3 added lines, in `ChatView.swift`, ledger row). The registry re-matches each view's own text and exposes `target(...)` (view plus local range) for placement. Rejected: attributed-string backgrounds (fight `updateNSView` equality, selection and the measuring contract), a query in the SwiftUI environment (invalidates every gated row per key), matching views to rows by geometry (preference-key timing).
Scrolling: a message with mounted views is scrolled inside the transcript `NSScrollView` to put the hit about 35% down the viewport (skipped when it is already visible below the 48 pt bar); an unmounted row is first revealed through `ChatScrollEngine.explicitMessageRequested` (browsing mode, `proxy.scrollTo`), then placed when its views register (passes at 50 and 250 ms), with the reveal re-issued every 250 ms at most 6 times. A scroll the Mac surface did not write is read as the reader browsing, so the engine does not pull back to the latest message.
Controller behaviour: after a transcript change the previous order is merged with the new one so the current hit falls to the nearest survivor when its message was removed (never jumps to the newest); the controller hops past `willSet` (availability and "loaded only" are read after the write) and Next / Previous step even while a refresh search is queued. Bar availability is tied to the chat route (switching to Bots / Cron / Kanban closes the bar). VoiceOver announcements post only for settled results (typed query after debounce, or an explicit step), deduped on query and label. Count keys are `%1$@ of %2$@` and `%1$@ of %2$@+` with locale-formatted number strings (the l10n checker rejects two integer placeholders in one key); the 13 non-English translations are model translations flagged for native-speaker review.
Cmd-F routing (supersedes the per-message half of D10): in the main window with chat shown and a find controller present, focus in the chat (nothing, the composer, a message view, the transcript, the find field) opens chat find; focus elsewhere (sidebar list, session search field) keeps Search Sessions; Bots / Cron / Kanban and group-chat rooms keep Search Sessions. Search Sessions also has its own Edit item with no key equivalent. Edit > Find > Find... (the per-message bar) stays without a key. Cmd-F, Cmd-G, Cmd-Shift-G do nothing under a sheet or in a floating panel (Quick Ask). In D21 session windows (`conduit-session` prefix; `MacChatFindActions.isSessionWindow` is the one place with the literal, swap for `MacSessionWindows.isSessionWindow` after D21 lands) they fall back to the pre-D23 behaviour: the focused message view's own find bar, Next and Previous via `performFindPanelAction`; with no find-capable message view focused they do nothing. The Cmd-G items needed no placement change (ours win the key without moving the group). Cmd-G opens chat find from sidebar focus while Cmd-F goes to Search Sessions there (intentional asymmetry).
Known gaps: counts for rows that are not built come from the projection (callout titles, columns, math and mermaid blocks can differ from what is drawn; common blocks are pinned by `MacChatFindParityTests`); not searched: system rows, collapsed thinking / tool text, the streaming tail, image alt text and math blocks (not drawn as selectable text); with no gateway media resolver a raw `MEDIA:` tag is drawn but not projected; no search of unloaded history ("Loaded messages only" shows when older pages exist). Not verifiable headlessly: real hardware Return, Shift-Return and IME in the field, session-window Cmd-G with the per-message bar open (D21 unmerged), and the landing position of `scrollTo` into a far unbuilt row on a very long session (no manual pass was run; release gate, see SMOKE_CHECKLIST).
